## 0. Назначение документа

Этот документ объединяет без функциональных потерь планы V1-V4, red-team-аудит,
три инженерные экспертизы, действующую доктрину интеграции Yalken Design OS и

Definition of Done. Полный Program DoD наступает только после завершения всей
программы.

## 3. Закон полноты

Все возможности V1-V3 входят в `CAPABILITY_BACKLOG`. Каждая capability обязана
иметь один статус:

```text
PLANNED | ACTIVE_STAGE | DELIVERED | DEFERRED | REPLACED | DEPRECATED
```

Ни одна возможность не исчезает молча. `DEFERRED`, `REPLACED` и `DEPRECATED`
требуют явного решения владельца, причины, оценки миграции и rollback. Наличие
capability в полном плане не делает её блокером текущего этапа.

## 5. Формула Yalken Design OS

```text
PRODUCT_TRUTH + COMMAND_MEANING + COMPUTED_INTERFACE_FORM = YALKEN
```

### 5.1 Product Core

Product Core владеет:

- рукописью и структурой;
- авторскими сущностями и связями;
- картами и их содержанием;
- доменными инвариантами;
- миграциями и recovery semantics;
- каноническими операциями и их результатами.

### 5.2 Command Kernel

Command Kernel владеет:

- стабильными command IDs и версиями;
- availability и capability policy;
- валидацией payload;
- маршрутизацией;
- единственным разрешённым путём продуктовых мутаций;
- повторной capability-проверкой при каждом dispatch.

### 5.3 Design OS

Design OS владеет только вычисляемой формой:

- surfaces и typed slots;
- layout, profiles и workspaces;
- видимостью и representations команд;
- platform projection и fallback;
- accessibility overrides;
- shell snapshots, safe reset и restore last stable.

Design OS не владеет Atlas truth, картами, рукописью, командами, storage,
recovery, evidence или языковым анализом.

### 5.4 Закон двух плоскостей

Каждый модуль подключается дважды, через независимые контракты:

```text
PRODUCT_PLANE:
Domain -> Commands -> Events -> Queries/Projections -> Product Ports -> Adapters

INTERFACE_PLANE:
Feature Contribution -> Command Catalog -> Domain Projection -> Surface Manifest
-> Design OS Resolver -> Resolved Snapshot -> Renderer Adapter
```

Product port и Design OS port нельзя объединять в универсальный фасад.

### 5.5 Кандидаты product boundaries

Точный набор определяется Stage 00 по фактическим seams. Нормативные семейства,
которые могут потребовать port и adapter:

- `ProjectPersistencePort` — project files, transactions, backup и recovery;
- `AnalysisExecutionPort` — запуск изолированного анализа;
- `LanguageAnalysisPort` — versioned language capability;
- `WorkerExecutionPort` — process/thread boundary и cancellation;
- `ExportDestinationPort` — filesystem/share destination без path authority у UI;
- `AttachmentPort` — bounded import и чтение вложений;
- `CollaborationTransportPort` — только после активации collab stage.

`UiNotificationPort`, `ProjectionPort` и универсальный `PersistencePort` не
создаются автоматически: неоднозначные имена скрывают authority. Внутренний
module call остаётся обычным module call, пока port не оправдан границей.

Interface plane использует направленные read-only/intent-only контракты
действующей doctrine: command catalog, command dispatch intent, domain
projection, viewport, shell state, shell projection, diagnostics и extension
manifest contribution.

Стабильным является не полный набор будущих доменных типов, а минимальный

- identity и ownership;
- transaction coordinator;
- capability enforcement;
- operation envelope;
- provenance и evidence identity;
- revision и generation guards;

Версионируемо развиваются:

- Time и Continuity;

- exporters и importers;

Новый port, registry или feature pack вводится только если существует реальная

Manifest не является основанием создавать runtime registry.

## 7. Классы состояния

```text
PROJECT_STATE: канонические авторские данные и доменные решения
AUTHORING_WORKING_STATE: несохранённый текст и черновое содержимое с no-loss duty
DERIVED_STATE: перестраиваемые versioned generations
SHELL_STATE: layout, profile, visibility и last stable UI snapshot
TRANSIENT_STATE: hover, drag preview, selection paint и session-only данные
```

Правила:

- Project persistence и shell persistence не разделяют authority.
- Несохранённый текст и несохранённый узел карты нельзя потерять при UI reset.
- Derived cache можно удалить и полностью пересобрать.
- ViewState можно удалить без потери содержательной карты.
- Product recovery не зависит от shell snapshot.

## 19. История, комментарии и совместная работа

### 19.1 Один источник операционной истины

Не создаются два конкурирующих append-only журнала.

```text
OperationLedger: канонические product operations и replay identity
RevisionHistory: текстовые snapshots/diffs как проекция операций и сохранений
Decision: семантическое доменное событие/запись внутри той же transaction identity
CommentThread: отдельная доменная сущность, привязанная к stable anchor
```

Decision не является вторым event bus. Keystroke, drag и zoom не создают
semantic Decision.

### 19.2 Operation envelope

```text

projectId
commandId
commandVersion
baseRevision
targetIds
correlationId
payload
createdAt
```

Capability revalidation выполняется в Command Kernel, а не доверяется
сохранённому snapshot из envelope.

### 19.3 Транзакционная граница

Одна canonical transaction атомарно фиксирует:

- author mutation;
- operation record;
- semantic Decision, если применимо;
- revision increment;
- transactional outbox / projection invalidation.

Derived rebuild запускается только после commit.

### 19.4 Collab readiness

- IDs collision-safe и transport-neutral;
- Commands не зависят от transport;
- comments и anchors существуют до collab;
- deterministic replay доказан до multi-writer;
- CRDT или иной transport не становится Product Core;
- сеть получает отдельные capability, adapter и security boundary;
- offline baseline продолжает работать без сети;
- network collab не активируется до отдельного platform/release stage.

## 19A. Тарифы и сохранность Pro-данных

Atlas, автоматические проекции, ручные интеллект-карты, continuity и advanced
graph относятся к Pro capability layer. Лицензия не меняет project format,
Product Core или Design OS profile.

При открытии Pro-проекта без активной Pro capability:

- рукопись продолжает редактироваться;
- все Pro author data сохраняются без потерь;
- неизвестные поля не удаляются;
- существующие Pro-комментарии читаются;
- сложная аналитика не пересчитывается;
- stale derived data помечается адресно, а не для всего проекта;
- полный архив и recovery доступны;
- UI не превращается в лес замков;
- повторная активация Pro использует сохранённые author data и перестраивает
  derived generations.

Истечение тарифа никогда не удаляет карты, Atlas decisions, calendar,
continuity или evidence.

### 19A.1 Licensing Decision Gate

До первого contour, который реально ограничивает Pro capability, агент
автономно закрывает `LICENSE_MODEL_DECISION`:

- источник entitlement;
- полностью локальная проверка или platform receipt;
- работа без обязательного аккаунта;
- offline grace и поведение при недоступной проверке;
- перенос на новое устройство;
- восстановление после переустановки;
- возврат, отмена и истечение;
- clock rollback и damaged license state;
- privacy и отсутствие телеметрии;

Канонический default для desktop offline-first: подписанный локальный
entitlement, проверяемый встроенным public key без обязательного аккаунта,

key никогда не попадает в приложение, репозиторий, plan или receipts.

Если конкретный commercial channel ещё не выбран, агент реализует
transport-neutral entitlement contract и локальный adapter, продолжая всю
остальную программу без ожидания внешнего решения.

## 20. Хранение, поколения и recovery

### 20.1 Author data

- атомарная запись;
- readable recovery;
- backups;
- checksum и schema version;
- unknown-field preservation;
- downgrade-safe read where declared;
- полный проектный архив.

### 20.2 Derived store

Полное поколение физически не копируется после каждой правки.

```text
GenerationManifest
  -> content-addressed SceneArtifact shards
  -> Aggregate shards
  -> Projection indexes
  -> analyzer and schema versions
  -> sourceRevision
```

Публикация выполняется compare-and-swap по source revision и generation.
Устаревшие результаты отбрасываются. Root доверия не переносится в Core без
отдельной threat model; целостность доказывается manifest hashes, source
revision, reproducible rebuild и защищённой delivery attestation.

### 20.2.1 Integrity scope и threat model

Текущая manifest/hash-модель доказывает:

- обнаружение случайного повреждения;
- связь с source revision;
- stale generation rejection;
- воспроизводимость rebuild;
- целостность локальной generation в заявленных пределах.

Она не заявляет защиту от злоумышленника, способного одновременно изменить
derived artifacts и локальные manifests. До первого внешне проверяемого,
криптографически подписываемого или hostile-environment derived artifact
агент автономно создаёт `ATLAS_ATTESTATION_THREAT_MODEL_DECISION`: активы, attacker
capabilities, trust root, key custody, rotation, revocation, verification и
recovery. До закрытия контура агент просто не заявляет tamper-proof и продолжает
все остальные dependency-ready contours.

### 20.3 Retention и compaction

- текущая подтверждённая generation;
- последняя известная рабочая generation;
- bounded diagnostic generations;
- content-addressed shards с reference counting;
- безопасная garbage collection;
- bounded OperationLedger snapshots без потери replay semantics;
- attachments quota и diagnostics;
- ViewState debounce и compaction.

### 20.4 Recovery drill

Проверяется:

- сбой до commit;
- сбой после author commit до invalidation;
- сбой во время derived build;
- stale generation publication;
- удаление всего cache;
- reopen и deterministic rebuild;
- повреждение одного shard;
- project on external filesystem;
- восстановление без shell state.

## 21. Миграции

Legacy Mind Map TXT обрабатываются строгим протоколом:

1. Read-only inventory и hash исходника.
2. Machine-defined empty criterion: ноль значимых grapheme clusters после
   разрешённого trim.
3. Preview результата: Note, Idea или Manual Map.
4. Shadow migration без изменения оригинала.
5. Validation и round-trip content hash.
6. Marker `PREPARED`.
7. Atomic activation.
8. Reopen validation.
9. Marker `COMMITTED`.
10. Оригинал сохраняется до явного подтверждения автора.
11. Rollback восстанавливает старое чтение и удаляет только новый результат.

Проверяются empty, meaningful, malformed, invalid encoding, interrupted,
collision, idempotent resume и rollback fixtures. Generic legacy guard не
заменяет сквозной пользовательский сценарий.

### 28.1 Gate modes

`PR` блокирует только затронутые critical invariants и focused checks.

`RELEASE` дополнительно блокирует packaged critical journey, recovery,
security и active-platform smoke.

`PROMOTION` активирует новые capability claims только после negative tests,
владельческого решения и доказанной rollback path.

`NIGHTLY` выполняет тяжёлые corpus, scale, fuzz и full rebuild проверки.

Новые Atlas claims advisory до активации соответствующего programStage. Они не
могут блокировать Writer v1.

### 28.1.1 Mapping в существующую инфраструктуру

Эти четыре имени являются семантическими режимами плана, а не требованием
немедленно расширить CLI runner.

Stage 00 создаёт `GATE_MODE_ADAPTER_MAP`:

```text
PLAN_PR        -> existing prCore/focused CI route
PLAN_RELEASE   -> existing release route
PLAN_PROMOTION -> existing promotion route
PLAN_NIGHTLY   -> scheduled heavy suites outside blocking PR path
```

Если существующий `run-tests.js` принимает только `release` и `promotion`,
предпочтителен mapping через существующие project-native commands. Runner
расширяется только если mapping не может честно выразить required behavior.

Stage 00 также создаёт `ATLAS_GATE_FAMILY_MAP`, связывающий семь семейств с
существующими `TOKEN_CATALOG`, `FAILSIGNAL_REGISTRY`, `modeMatrix`, executable
checks и negative fixtures. Второй параллельный token/failsignal registry
запрещён.

### 28.2 Защита от false green

- sourceBinding указывает на executable behavior, не на заполненный JSON;
- позитивный тест без negative fixture недостаточен;
- packaged test запускает реальный пользовательский маршрут;
- perf использует утверждённый corpus и hardware profile;
- evidence проверяется не только на наличие, но и на правильную reattachment;
- capability проверяет фактический analyzer result;
- attestation не подписывает сама себя;
- network delivery failure отделяется от local product regression;
- registry/control-plane проверяется на merged target HEAD;
- stale receipt не переиспользуется.

## 30. Execution order

Исполнение строго последовательное для одного autonomous executor. Независимая
работа возможна только если репозиторный orchestrator явно выделяет отдельный
bounded contour и сохраняет одного accountable writer для control-plane файлов.

### 30.1 Execution control

```text
TARGET_BRANCH: RESOLVE_AT_STAGE_00
ORIGINAL_BASE_SHA: RESOLVE_AT_STAGE_00
EXPECTED_TARGET_HEAD: PENDING_P1_DIGEST_DELIVERY_COMMIT
ACTIVE_PROGRAM_STAGE: STAGE_00
ACTIVE_PLATFORM_STAGE: RESOLVE_AT_STAGE_00
BASELINE_CHECK_STATUS: UNKNOWN_UNTIL_STAGE_00
REPO_REQUIRED_CHECKS: RESOLVE_FROM_ACTIVE_REPO_POLICY
EXECUTION_STATUS: IN_PROGRESS
NEXT_STAGE: STAGE_00
```

Mutable execution state не получает вручную поддерживаемый self-hash. Его
целостность связывается с git SHA, artifact IDs и автоматически созданными
receipts. Расхождение state сначала вызывает read-only reconstruction.
Validated rebind выполняется только в пределах active canon: если repo policy
требует явного Base SHA, standing carte blanche разрешает агенту самостоятельно
выбрать и записать свежий безопасный SHA после проверки combined diff. Тихий
непроверенный rebase запрещён. Расхождение tracker-а само по себе не создаёт
STOP.

миграцию, которую придётся выбросить на следующем этапе.

## 31. Delivery protocol

Для каждого stage:

1. Перечитать active canon и этот план.
2. Получить свежий remote HEAD и binding по правилам репозитория.
3. Изолировать worktree при dirty canonical checkout.
4. Зафиксировать `FEATURE_INTEGRATION_MANIFEST_V1` только затронутого vertical
   contour.
5. Назвать один пользовательский outcome, один rollback и focused checks.
6. Реализовать через существующие seams; новый port только при доказанной
   границе.
7. Выполнить focused checks.
8. Выполнить phase checks только на границе риска.
9. Commit сразу после смыслового результата.
10. Push, PR, CI, merge и post-merge verification по repo policy.
11. Обновить factual docs только после принятого runtime.
12. Следующий contour начинается только после завершённой delivery chain.

Один vertical contour может затрагивать Core, Commands, storage и UI в одной
поставке. Отдельный PR на каждый слой запрещён как process-tax, если нет
отдельного риска или независимого rollback.

## 32. No-stop execution policy

Внутри objective нет routine STOP и approval gates.

- Конфликт реализации с active canon решается выбором совместимого подхода.
- Неясный владелец данных разрешается по существующей authority hierarchy.
- Небезопасная migration заменяется shadow migration и обратимым adapter path.
- Новая dependency проходит автоматический dependency contour.
- Недоступная сеть заменяется local fixture и deferred external activation.
- Недоступная платформа получает adapter contract, emulator/fixture proof и
  продолжение доступных platform stages.
- Недоказанный invariant открывает repair contour, а не формальный PASS.
- Drift вызывает fetch, combined-diff reconciliation и новый точный base.

Если определённое внешнее действие нельзя выполнить локально без платежа,
чужих private data, необратимого разрушения или live-production authority, оно
маркируется `EXTERNAL_ACTIVATION_PENDING`, заменяется проверяемым локальным
контрактом и не останавливает остальные contours. Goal остаётся активным до
закрытия максимально достижимого Program DoD.

## 33. Критические инварианты

1. Анализ и карта не меняют рукопись без отдельной подтверждённой команды.
2. Каждая product mutation проходит Command Kernel.
3. UI и worker не получают прямой Core/storage authority.
4. Автоматический Atlas не выполняет merge сущностей.
5. Автоматический Atlas не создаёт смысловые отношения.
6. Каждый автоматический вывод имеет проверяемое narrative evidence.
7. Неподдерживаемый язык остаётся exact-only.
8. Оригинальный Unicode-текст сохраняется побайтно или по заявленному
   round-trip контракту.
9. Derived cache удаляем и перестраиваем.
10. Stale async result не публикуется.
11. Project, authoring, derived, shell и transient state не смешиваются.
12. UI reset не теряет несохранённый текст или черновое содержимое карты.
13. Карта не создаёт второй скрытый источник истины.
14. ViewState не содержит единственную копию авторского содержания.
15. Design OS управляет формой, но не доменной семантикой.
16. Capability проверяется при dispatch.
17. Внешний input недоверен до adapter validation.
18. Тяжёлая работа не выполняется в typing hot path.
19. Все graph actions имеют доступный невизуальный эквивалент.
20. Истечение тарифа не удаляет author data и не блокирует recovery/export
    согласно отдельной продуктовой политике лицензирования.

## 34. Program Definition of Done

Программа завершена только когда:

- четыре канонические проекции и неограниченные ручные карты работают через
  общий Graph Interaction Contract;
- автоматическая и ручная карта используют общий Workbench, но разные authority;
- Product Core остаётся единственной доменной истиной;
- Command Kernel остаётся единственным write path;
- Design OS интегрирует surfaces через manifests и typed slots;
- Atlas доказателен, обратим и не переписывает рукопись;
- время, вымышленный календарь и Continuity Ledger полностью работают;
- GLOBAL language baseline работает для любого Unicode-языка;
- заявленные BASIC/DEEP языки независимо сертифицированы;
- mixed-language, CJK, RTL, IME и Unicode edge cases доказаны;
- manual maps, Atlas decisions и author data входят в recovery;
- derived cache полностью перестраивается;
- history/comments/collab не создают второй журнал истины;
- импорт, экспорт, round-trip и полный архив доказаны;
- performance budgets выполнены на утверждённых corpora и hardware;
- graph accessibility и fallback parity доказаны;
- активированные platform stages прошли packaged verification;
- factual docs соответствуют реальному runtime;
- ни одна capability полного плана не потеряна молча.

### 35.3 Осознанно не принятые буквально предложения

- Не фиксируется искусственное число `три registry` или `пять ports`: действует
  проверяемый закон необходимости границы.
- Не фиксируется WASM как обязательный language engine до license/benchmark
  decision.
- Не фиксируется Yjs или иной CRDT как collab Core; transport выбирается позже.
- Derived root hash не переносится в Core manifest без отдельной threat model.
- UTF-16 не запрещается глобально; offset domains конвертируются на adapter
  boundary.
- Docs write не получает обход repo delivery policy; report-only остаётся
  no-write.
- Не разрешается искусственная параллельность одного исполнителя и гонка
  control-plane файлов.
- План не блокирует Writer v1. Его repo adoption выполняется агентом отдельным
  contour через штатный commit, PR и merge под standing carte blanche.
- Произвольные performance числа не становятся каноном до калибровки.
- Полный Graph Workbench не обязан иметь один физический renderer на desktop,
  web и mobile; едины interaction/projection contracts.

## 36. Финальная формула

> Универсальный Stable Kernel хранит авторскую истину и безопасные операции.
> Языковые анализаторы понимают конкретную речь настолько глубоко, насколько
> это доказано. Автоматический Atlas показывает наблюдения и доказательства.
> Ручные карты позволяют автору думать как угодно. Graph Workbench связывает
> эти миры визуально, а Yalken Design OS придаёт им форму, не присваивая их
> смысл.

## 38. Standing approval и целостность контракта

### 38.1 Immutable contract

Immutable contract находится между markers:

```text
BEGIN_IMMUTABLE_PRODUCT_AND_EXECUTION_CONTRACT_V5
END_IMMUTABLE_PRODUCT_AND_EXECUTION_CONTRACT_V5
```

При startup executor вычисляет SHA-256 точных UTF-8/LF bytes между markers,
исключая marker lines, без BOM. Digest сохраняется только в mutable state и
startup receipt, поэтому не является self-referential.

### 38.2 Standing authority state

```text
AUTHORITY_STATUS: STANDING_CARTE_BLANCHE
AUTHORITY_SOURCE: OWNER_INSTRUCTION_IN_CURRENT_THREAD
AUTHORITY_GRANTED_AT: 2026-07-29

```

Текущее поручение владельца является полным standing authority для objective.
Никакие review/approval gates между contours не создаются.

Если техническая адаптация immutable contract не меняет Product North Star,
Stable Kernel, Program DoD или authority boundary, агент повышает plan revision,
пересчитывает digest, фиксирует Decision Log и продолжает. Если предложенное
изменение вышло бы за objective, агент его не делает и выбирает совместимый
вариант внутри утверждённой цели.

### 38.3 No brittle state hash

У mutable state нет ручного `CURRENT_STATE_SHA256`. Истина исполнения
восстанавливается из:

1. Git/remote identity;
2. branch, PR и merged commit;
3. CI terminal results;
4. current worktree diff;
5. terminal receipts;
6. monotonic `STATE_REVISION` и transition log.

Неожиданная revision вызывает reconciliation и competing-writer check, а не
автоматический hard stop из-за контрольной суммы текста.

## 39. Project binding

До любой write-операции агент обязан:

1. Найти applicable `AGENTS.md` и active canon resolver.
2. Определить Git root по фактическому репозиторию.
3. Проверить remote URL, default branch и stable markers.
4. Вычислить `PROJECT_FINGERPRINT`.
5. Убедиться, что mutable targets принадлежат этому fingerprint.
6. Проверить Git status, branches, worktrees, PR и active writers.
7. Не использовать worktree, receipt или plan другого fingerprint.
8. Не мутировать Obsidian, T7 archives или внешние исследования: они read-only
   evidence dependencies.

Если canonical checkout грязный пользовательскими изменениями, агент не
останавливается и не трогает их. Он создаёт или находит отдельный linked
worktree по правилам репозитория. Для T7-Secure сначала проверяются mount,
writability, encryption identity и UUID из `AGENTS.md`.

## 40. Единственный план и единственный writer

- V5 является единственным executable plan этой mission.
- V1-V4 остаются read-only predecessors и не получают mutable state.
- Одновременно активен один state-changing contour.
- Один основной агент владеет state, branch, PR и delivery chain.
- Read-only subagents могут исследовать, но не писать plan/repo/runtime.
- Новый contour не начинается до merge или явного terminal outcome предыдущего.
- Plan-owned branch и worktree удаляются только после доказанного merge и
  фиксации нового remote HEAD.

Competing writer определяется по несовпадающим state revision, активной lease,
plan-owned branch/PR или неожиданным изменениям write set. Сначала выполняется
reconciliation. При доказанной одновременной мутации агент не создаёт STOP:
ждёт terminal transition текущего writer-а, выполняет read-only подготовку
следующего contour либо продолжает непересекающуюся проверку, сохраняя WIP=1.

## 43. Dynamic Contour Compiler

### 43.1 Зачем он нужен

Сейчас невозможно честно указать exact файлы и команды всех многолетних
contours: будущий runtime изменится после каждого merge. Выдуманные заранее
write sets создали бы false precision.

Поэтому перед каждым macro-stage агент выполняет read-only compilation:

1. Перечитывает active canon и factual runtime текущего merged HEAD.
2. Берёт только acceptance и scope соответствующего Stage 00-11.
3. Строит минимальную линейную очередь contours.
4. Проверяет, что каждый contour даёт один пользовательский outcome.
5. Заполняет точный `CONTOUR_ACTION_ENVELOPE`.
6. Записывает очередь в mutable state/contour queue.
7. Не меняет North Star, stable invariants и Program DoD.
8. Сразу начинает первый ready contour.

### 43.2 Split triggers

Contour автоматически делится, если одновременно выполняется хотя бы одно:

- больше одного независимого пользовательского outcome;
- больше одной migration family;
- больше двух действительно новых architectural ports;
- больше одного dependency/renderer/language-engine decision;
- независимые rollback boundaries;
- UI и storage changes нельзя доказать одним critical journey;
- write set слишком широк для осмысленного review;
- focused checks превращаются в полный release suite.

Split не удаляет capability и не требует user approval, если цель,
архитектура, order dependencies и Program DoD не меняются.

## 45. Standing authority

Агенту заранее разрешены обычные действия внутри mutation-owner

## 46. Autonomous decision policy

Агент самостоятельно принимает и фиксирует в Decision Log:

- технический подход;
- внутреннюю декомпозицию contours;
- выбор renderer после benchmark;
- dependency в пределах коммерчески совместимой лицензии и security policy;
- language engine после license/size/performance проверки;
- локальную licensing architecture;
- schema evolution и обратимые migrations;
- recovery и rollback approach;
- исправление CI и merge conflicts;
- platform adapter;
- переносимые UI/UX решения внутри утверждённого Design OS;
- изменение тактики исполнения без изменения Product North Star.

Никаких user approval gates внутри objective нет.

Если путь потребовал бы платёж, юридически значимое внешнее обязательство,
раскрытие чужих private data, необратимое уничтожение, force-push, обход branch

approval: он выбирает бесплатный, локальный, обратимый, non-production путь и
продолжает. Такой внешний путь остаётся `NOT_APPLICABLE_TO_CURRENT_AUTONOMOUS_RUN`.

Если конкретная capability физически невозможна без внешнего ресурса, агент
создаёт совместимый adapter/contract, fixture и local proof, помечает только
внешнюю активацию `EXTERNAL_ACTIVATION_PENDING` и продолжает все остальные
contours. Весь goal не завершается, пока остаётся безопасный способ закрыть
Program DoD локально или через доступную инфраструктуру.

Force-push и обход branch protection запрещены.

## 48. Drift и merge continuity

Перед каждым contour агент делает fetch и сравнивает target HEAD с expected.

1. Если drift не пересекает write set и repo policy разрешает safe update,
   агент обновляет binding, фиксирует decision и продолжает.
2. Если требуется обычное разрешение merge conflict, агент сохраняет обе
   стороны и повторяет invalidated checks.
3. Если active canon требует явный Base SHA при конкретном drift, standing
   carte blanche разрешает агенту выбрать свежий target SHA после combined-diff
   проверки, записать rebind receipt и продолжить без запроса.
4. Если PR уже merged другим разрешённым процессом, агент проверяет merged SHA,
   sealing receipt и продолжает.
5. Если target содержит эквивалентную реализацию, агент подтверждает acceptance,
   закрывает contour как `SATISFIED_BY_TARGET` и не дублирует код.

Ни один успешный merge не теряется из state: merged SHA становится
`CURRENT_BASE_SHA`, `EXPECTED_TARGET_HEAD` и evidence identity следующего
contour.

## 49. Orphan recovery

Перед новой mutation незавершённая операция классифицируется:

```text
ACTIVE_HEALTHY
COMPLETED_UNRECORDED
INTERRUPTED_RESUMABLE
INTERRUPTED_ROLLBACK_REQUIRED
AMBIGUOUS_SIDE_EFFECT
```

- `ACTIVE_HEALTHY`: ждать/следить без duplicate process.
- `COMPLETED_UNRECORDED`: проверить postconditions и восстановить receipt.
- `INTERRUPTED_RESUMABLE`: продолжить с доказанной точки.
- `INTERRUPTED_ROLLBACK_REQUIRED`: откатить только plan-owned incomplete work.
- `AMBIGUOUS_SIDE_EFFECT`: выполнить read-only reconciliation; hard block лишь
  когда side effect нельзя безопасно установить или компенсировать.

## 50. Recovery ladder

При failure агент обязан:

1. Собрать terminal evidence и failure signature.
2. Проверить process liveness и не прерывать healthy long-running operation.
3. Отделить собственную regression от baseline, flaky, network и external fail.
4. Исправить текущую реализацию и повторить только invalidated checks.
5. Один раз повторить тот же подход только при доказанной flaky/external причине.
6. Применить другой технический подход в утверждённом scope.
7. Разделить contour или добавить bounded repair/integration contour.
8. Откатить только незавершённые plan-owned изменения contour и реализовать
   заново.
9. При внешнем ожидании продолжить независимый ready contour, если order и
   write sets это допускают.
10. После трёх materially different безопасных подходов выполнить architecture-
    preserving replan, разбить contour и продолжить новым подходом. Формальный
    `BLOCKED` внутри objective не используется.

Обычные test failures, red CI, dirty canonical checkout, merge conflict,
неоднозначность реализации, drift и отсутствие необязательного инструмента не
являются причинами STOP или запроса approval.

Provider-backed execution для этого плана по умолчанию `NOT_APPLICABLE`.
Если поздний research contour использует внешний provider, действуют:

```text
provider_dispatches_per_role: 1
pre_dispatch_recovery_attempts: 1
ambiguous_dispatch_retries: 0
```

## 51. Test economy

- focused checks после каждого изменения;
- affected checks перед commit/PR;
- phase checks на границе macro-stage;
- full/release checks только на required boundary и final identity;
- heavy corpus/scale/fuzz в nightly;
- одинаковый full suite не повторяется без нового SHA/input/reason;
- PR-head PASS не доказывает merged-target PASS;
- predecessor evidence переиспользуется только при exact diff proof;
- candidate, меняющий policy, gate, validator, workflow, dependency, config,
  runtime-sensitive path или receipt schema, требует candidate-specific checks;
- exit code 0 без правильного scope и artifact identity не закрывает acceptance.
